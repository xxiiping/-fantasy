# 001 · 单测「假绿」：测试通过了，但测的不是新代码

| 项 | 内容 |
| --- | --- |
| 日期 | 2026-10-23 12:02 |
| 阶段 | M0 |
| 类型 | 工具链假设错误（不是业务 bug） |
| 发现方式 | 主动做变异测试 |
| 严重度 | 高 —— 会让后续所有验收失去意义 |

---

## 背景

`GameState` + 11 条单测写完后，第一次 `test_run` 就 **11/11 全绿、56 条断言全过**。

一次就全绿这件事本身可疑。如果测试根本没接在真实代码上，也会是全绿。所以我没有直接推进 M1，而是先验证「这些测试到底能不能抓错」。

## 做法：变异测试

故意把 `GameState.push_rune()` 的失败判定改错一位：

```diff
- if attempts_left <= 0:      # 正确：第 2 次错即失败
+ if attempts_left < 0:       # 变异：允许第 3 次输入
```

这是这道题最经典的 off-by-one —— 把「2 次机会」写成「3 次机会」。

改完直接重跑测试。

## 第一次结果：**11/11 依然全绿**

测试没有发现任何问题。说明测试跑的根本不是磁盘上那份代码。

## 根因

- 测试脚本用 `preload("res://scripts/core/game_state.gd")` 持有脚本引用；
- 我用文件写入的方式直接改磁盘，**编辑器的 GDScript 缓存没有失效**；
- `test_run` 复用了缓存里的旧版本，于是「用旧代码验证旧代码」，必然全绿。

`test_run` 的返回里其实带了 `cache_warning`（"Preloaded GDScript dependencies may be stale after source edits"），但我第一眼把它当成普通提示忽略了。**这是本次真正的教训：警告不是噪音。**

## 修复：改文件后必须 scan

正确的工作流是：

```
修改脚本 → filesystem_manage(scan) → test_run
```

漏掉 `scan` 就会拿到假绿。

## 修复后的复验：变异被抓到了

| 测试 | 结果 | 失败消息 |
| --- | --- | --- |
| `test_05_second_wrong_ends_in_failure` | FAIL | 连续 2 次错误必须结算 |
| `test_06_settled_blocks_all_input` | FAIL | 结算后仍在接受输入 |
| `test_07_reset_restores_every_field` | FAIL | 脏状态没造出来 |
| 其余 8 条 | PASS | — |

**恰好 3 条、恰好是这 3 条** —— 说明测试确实接在真实模块上，且覆盖到了 off-by-one。

还原代码 + scan 之后，11/11 全绿（这次是真绿）。

## 结论与流程修正

1. **「全绿」不能当作验收通过的证据**，除非先证明测试能变红。
2. 每次改脚本后，`scan` 是必须步骤，不是可选步骤。
3. 变异测试要作为一次性检查，在关键模块（判定逻辑）上做一次，不进常规循环 —— 它证明的是测试的有效性，不是代码的正确性。

## 顺带发现

`script_patch` 在脚本已被 `preload` 持有时会返回 `reload_reason: "parse_error"`（GDScript reload failed, error code 43），但脚本本身语法完全正常（`script_manage(find_symbols)` 能正常解析出 8 个函数）。
**不要被这个错误码误导去改代码** —— 应该改用 `edit + scan` 的路径。
