## 6. 自定义资源注册（填空）

**`class_name`**

```gdscript
class_name InventoryItem   # ← 就是它
extends Resource

@export var id: int = 0
```

`extends Resource` 只是让它成为资源，**只有加了 `class_name` 才会注册成全局类型**，从而出现在编辑器「新建资源」的类型列表里，也能被 `@export` 的类型标注引用。

> 补充：若只想让脚本出现在创建对话框而**不想**污染全局命名空间，也可以在 `@export` 里写 `@export var x: Resource`，但那样就失去了类型约束，检查器里也无法按类型筛选。

## 7. `_process(delta)` 与 `_physics_process(delta)`

### 调用时机

|       | `_process(delta)`         | `_physics_process(delta)`                 |
| ----- | ------------------------- | ----------------------------------------- |
| 频率    | 每个**渲染帧**一次，帧率可变          | 固定频率，默认 **60 Hz**                         |
| delta | 随帧率波动（掉帧时变大）              | 恒定，默认 `1/60`                              |
| 配置    | `application/run/max_fps` | `physics/common/physics_ticks_per_second` |
| 用途    | 视觉动画、UI、镜头插值              | 物理、碰撞、角色移动                                |

关键在 `physics/common/physics_ticks_per_second`（默认 60）与 `physics/common/max_physics_steps_per_frame`（默认 8）。引擎会把真实时间累积成固定步长的"物理拍"，一帧内可能需要连跑 0～8 次物理步。

### CharacterBody2D 为什么放在 `_physics_process`

**三条理由：**

1. **碰撞状态只在物理步里更新。** `move_and_slide()` 要拿当前帧的碰撞信息做滑动与贴地判定。在 `_process` 里调用，读到的是上一次物理步的旧数据，会出现穿墙、贴边抖动、卡角。
2. **固定步长让结果可复现。** 60 次/秒的固定 delta 下，同样的输入序列在不同机器上得到同样的轨迹；帧率一变，`_process` 的调用次数就变，运动结果跟着变。
3. **避免与物理线程抢状态。** `move_and_slide()` 会修改 `velocity` 与变换，物理引擎在另一个阶段读取它们；写在高频且时机不定的 `_process` 里，容易出现"这一帧移动了两次/没移动"。

### delta 与帧率的关系

位移必须与时间挂钩，不能按帧算：

```gdscript
# 错：按帧算，帧率一变速度就变
position.x += speed

# 对：按时间算
position.x += speed * delta

# CharacterBody2D 的推荐写法（move_and_slide 内部已处理 delta 与碰撞）
func _physics_process(delta: float) -> void:
    velocity.y += gravity * delta        # 重力也乘 delta
    velocity.x = input_dir * speed
    move_and_slide()
```

`_physics_process` 里 delta 恒为 1/60，所以运动稳定；`_process` 里 delta 忽大忽小，若还混用按帧计数（如 `frame += 1` 做动画），会出现高帧率下动画变快、低帧率下变慢。

> 一个容易忽略的点：`_physics_process` 里**不要**做重计算或多层循环，它每秒固定跑 60 次；重活应该甩给线程池或分帧处理，否则物理拍一拖长就会触发 `max_physics_steps_per_frame` 的钳制，表现为"游戏变慢"。

## 8. `Node.propagate_call()` 的行为

### 调用范围与顺序

```gdscript
propagate_call(method: StringName, args: Array = [], parent_first: bool = false)
```

- **范围：本节点 + 它的所有后代节点**，递归向下。**不会**传播到父节点或兄弟节点。
- **顺序**由 `parent_first` 决定：
  - `parent_first = false`（**默认**）：**先子后父**。深度优先，先把整棵子树处理完，最后才调用自己。
  - `parent_first = true`：**先父后子**。先调用自己，再递归子树。

这个默认值是刻意的：后序遍历（先子后父）适合"汇总/清理"——子节点先收尾，父节点再收摊；前序遍历适合"广播/下发"——父节点先设定状态，子节点再基于它响应。

### 与「向父节点传播」的区别

Godot **没有**内置的向上传播 API。`propagate_call` 是单向向下的，因为：

- **向下的路径是唯一的**（一棵子树），可以用一次递归完成；
- **向上的路径不唯一**（父节点可能有很多子节点），语义上无法界定"传给谁"，所以引擎不提供，需要自己写：

```gdscript
# 逐级向上，直到根
func propagate_up(node: Node, method: StringName, args: Array = []) -> void:
    var current := node
    while current != null:
        if current.has_method(method):
            current.callv(method, args)
        current = current.get_parent()
```

### 其他要点

- 方法不存在时会报错，批量调用前用 `has_method()` 防御更稳。
- 所有节点收到**同一份参数**，无法按节点定制；需要定制就用信号或显式遍历。
- 与 `call_group()` 的区别：`propagate_call` 按**树结构**递归，`call_group` 按**组**广播，与层级无关。暂停整棵 UI 子树用前者，通知所有敌人用后者。

## 9. 简易背包系统的 Resource 持久化

### 设计要点

题目要求「保存的是完整背包，不能只保存一个物品」。这里有一个必须绕开的限制：

> **`ResourceSaver.save()` 只接受 `Resource`，不能直接存 `Array`。**

所以背包本身也必须是一个 `Resource`，把物品数组放在里面。这是本题的核心考点。

结构：`Inventory`（Resource，容器）→ `Array[InventoryItem]`（物品）。保存 `Inventory` 时，物品数组会作为内联子资源一起写进 `.tres`。

### 代码

**① 物品**

```gdscript
# inventory_item.gd
class_name InventoryItem
extends Resource

@export var id: int = 0
@export var amount: int = 1
@export var item_name: String = ""


static func create(p_id: int, p_amount: int, p_name: String) -> InventoryItem:
    var item := InventoryItem.new()
    item.id = p_id
    item.amount = p_amount
    item.item_name = p_name
    return item
```

**② 背包（容器，也是保存单元）**

```gdscript
# inventory.gd
class_name Inventory
extends Resource

const SAVE_PATH := "user://inventory.tres"
const SAVE_VERSION := 1

@export var version: int = SAVE_VERSION
@export var items: Array[InventoryItem] = []


func add_item(id: int, amount: int, item_name: String) -> void:
    # 已有同类就叠加，避免背包里出现重复条目
    for item in items:
        if item.id == id:
            item.amount += amount
            return
    items.append(InventoryItem.create(id, amount, item_name))


func total_amount() -> int:
    var sum := 0
    for item in items:
        sum += item.amount
    return sum


func to_dict_list() -> Array[Dictionary]:
    # 便于写日志或做存档版本迁移
    var out: Array[Dictionary] = []
    for item in items:
        out.append({"id": item.id, "amount": item.amount, "name": item.item_name})
    return out
```

**③ 保存（追加到 `inventory.gd` 的 `Inventory` 类中）**

```gdscript
func save() -> Error:
    # 先写临时文件再替换，避免写到一半中断导致存档损坏
    var tmp_path := SAVE_PATH + ".tmp"
    var err := ResourceSaver.save(self, tmp_path)
    if err != OK:
        push_error("背包保存失败：%s（错误码 %d）" % [tmp_path, err])
        return err

    err = DirAccess.rename_absolute(
        ProjectSettings.globalize_path(tmp_path),
        ProjectSettings.globalize_path(SAVE_PATH)
    )
    if err != OK:
        push_error("背包替换失败：%s（错误码 %d）" % [SAVE_PATH, err])
        return err
    return OK
```

**④ 读取（同样是 `Inventory` 的静态方法）**

```gdscript
static func load_from_disk() -> Inventory:
    if not ResourceLoader.exists(SAVE_PATH):
        # 首次运行没有存档，返回空背包，不是错误
        return Inventory.new()

    # CACHE_MODE_IGNORE：绕开加载缓存，否则读到的是内存里的旧实例，
    # 会出现"改了字段再读还是旧数据"的幽灵问题
    var loaded := ResourceLoader.load(SAVE_PATH, "", ResourceLoader.CACHE_MODE_IGNORE)
    if loaded == null:
        push_error("背包文件无法解析：%s" % SAVE_PATH)
        return Inventory.new()

    if not loaded is Inventory:
        push_error("背包文件类型不符，期望 Inventory，实际 %s" % loaded.get_class())
        return Inventory.new()

    return loaded as Inventory
```

### 读取方式与失败处理说明

| 情况             | 处理                           |
| -------------- | ---------------------------- |
| 存档不存在（首次运行）    | 返回空背包，**不打错误**，属于正常分支        |
| 文件存在但解析失败      | `push_error` 并返回空背包，保证游戏能继续进 |
| 类型不符（被改过/版本不符） | 同上，并记录期望类型与实际类型              |
| 写入失败（磁盘满/权限）   | 返回 `Error` 给上层，由 UI 提示"保存失败" |
| 写到一半中断         | 临时文件 + 原子改名规避，旧存档仍完整         |

### 另外三点工程考量

1. **必须写 `user://`**。`res://` 在导出后的包里是只读的，`ResourceSaver.save` 会直接失败。
2. **版本号**。`@export var version` 用于将来读旧档时做字段迁移（例如新增"耐久度"字段时给旧档补默认值）。
3. **不重复叠加**。`add_item` 按 `id` 合并，避免背包里出现多条同 id 记录——这是这类系统最常见的隐性 bug。

## 10. 通用子弹对象池（Object Pool）

### 设计思路

对象池要解决的是「频繁 `instantiate()` / `queue_free()` 造成的分配与 GC 抖动」。因此池对象在**归还时不能销毁，也不能只是隐藏**——隐藏的节点仍在跑 `_process`、仍参与碰撞，只是不渲染而已。

三个必须处理的状态残留：

| 残留    | 处理                                                                       |
| ----- | ------------------------------------------------------------------------ |
| 可见性   | `visible = false`                                                        |
| 逻辑运行  | `process_mode = PROCESS_MODE_DISABLED`（**仅隐藏不够**）                        |
| 碰撞    | `set_deferred("monitoring", false)` / `CollisionShape2D.disabled = true` |
| 运动    | `velocity = Vector2.ZERO`，位置/旋转归零或重置到炮口                                  |
| 计时/计数 | 生命倒计时、穿透次数、已命中列表清空                                                       |

### 与子弹脚本约定的重置接口

池不直接改子弹的内部字段（容易漏改），而是**约定一个方法**，由子弹自己负责恢复初始状态：

```gdscript
# 约定：子弹脚本必须实现（下面是节选，velocity / life_time / pierce_left /
# max_pierce / max_pierce 这些字段在子弹脚本里已经声明，此处省略）
func reset_for_pool(spawn_transform: Transform2D) -> void:
    global_transform = spawn_transform
    velocity = Vector2.ZERO
    life_time = 0.0
    pierce_left = max_pierce
    $CollisionShape2D.set_deferred("disabled", false)
    modulate = Color.WHITE
```

约定优于约定字段：子弹可以自定义任意状态，池只负责生命周期。

### 代码

```gdscript
# bullet_pool.gd
class_name BulletPool
extends Node

@export var bullet_scene: PackedScene
@export var initial_size: int = 32
## 池的增长上限；超出后复用最早归还的那颗，避免无限膨胀
@export var max_size: int = 256

var _free: Array[Node] = []
## 用集合记录"正在使用中"，顺便做重复回收检测
var _in_use: Dictionary = {}


func _ready() -> void:
    prewarm(initial_size)


## 预热：开局就把对象建好，避免战斗中第一次开火时卡一下
func prewarm(count: int) -> void:
    for i in count:
        if _free.size() + _in_use.size() >= max_size:
            return
        var bullet := _instantiate()
        _park(bullet)
        _free.append(bullet)


func get_bullet(spawn_transform: Transform2D) -> Node:
    var bullet: Node
    if not _free.is_empty():
        bullet = _free.pop_back()
    elif _free.size() + _in_use.size() < max_size:
        # 不够就现场补一个（题目要求）
        bullet = _instantiate()
    else:
        # 达到上限：直接抢一颗在用的（可选策略，视玩法而定）
        push_warning("子弹池已达上限 %d，复用最旧的一颗" % max_size)
        bullet = _in_use.keys()[0]
        return_bullet(bullet)

    _in_use[bullet] = true
    _unpark(bullet)

    # 交给子弹自己恢复状态
    if bullet.has_method("reset_for_pool"):
        bullet.reset_for_pool(spawn_transform)
    else:
        push_error("子弹 %s 缺少 reset_for_pool()，池约定被破坏" % bullet.get_class())

    return bullet


func return_bullet(bullet: Node) -> void:
    if bullet == null or not is_instance_valid(bullet):
        return

    # 防重复回收：不在"使用中"集合里说明已经还过了，直接忽略
    if not _in_use.has(bullet):
        push_warning("重复回收子弹，已忽略")
        return

    _in_use.erase(bullet)

    # 兜底清理，防止子弹脚本漏改
    if bullet is Node2D:
        bullet.position = Vector2.ZERO
    if "velocity" in bullet:
        bullet.set("velocity", Vector2.ZERO)

    _park(bullet)
    _free.append(bullet)


func get_active_count() -> int:
    return _in_use.size()


func get_pool_size() -> int:
    return _free.size() + _in_use.size()


# ---------------------------------------------------------------- 内部

func _instantiate() -> Node:
    var bullet := bullet_scene.instantiate()
    add_child(bullet)
    # 记下原始碰撞层，出池时按原值恢复，而不是硬编码一个数字
    if bullet is CollisionObject2D:
        bullet.set_meta("pool_layer", bullet.collision_layer)
        bullet.set_meta("pool_mask", bullet.collision_mask)
    return bullet


## 归还态：不渲染、不跑逻辑、不参与碰撞
func _park(bullet: Node) -> void:
    bullet.visible = false
    bullet.process_mode = Node.PROCESS_MODE_DISABLED
    if bullet is CollisionObject2D:
        # 物理回调期间不能直接改这些属性，必须延迟
        bullet.set_deferred("collision_layer", 0)
        bullet.set_deferred("collision_mask", 0)


## 出池态：恢复渲染、逻辑与碰撞
func _unpark(bullet: Node) -> void:
    bullet.visible = true
    bullet.process_mode = Node.PROCESS_MODE_INHERIT
    if bullet is Area2D:
        bullet.set_deferred("monitoring", true)
    if bullet is CollisionObject2D:
        bullet.set_deferred("collision_layer", bullet.get_meta("pool_layer", 1))
        bullet.set_deferred("collision_mask", bullet.get_meta("pool_mask", 1))


func _exit_tree() -> void:
    # 子弹都是本节点的子节点，会随池一起被释放；
    # 这里只需要把引用清掉，避免悬挂引用。
    _free.clear()
    _in_use.clear()
```

### 如何避免重复回收

三件事同时做，缺一不可：

1. **用集合而不是计数器**。`_in_use` 是 `Dictionary`，`return_bullet` 先查 `has()`，不在就说明已经还过了。计数器法在"同一帧多次触发 `area_exited`"时会算错。
2. **归还前先判 `is_instance_valid`**。子弹可能已经被别的逻辑 `queue_free()` 掉了。
3. **信号层面防御**。子弹的 `area_entered` / `body_entered` 回调里先判断 `if not is_inside_tree(): return`，避免归还后又触发一次。

### 可见性、碰撞、运动状态的残留

这是池最常见的"幽灵子弹"来源，具体表现与对策：

| 现象                                                                  | 原因                       | 对策                                              |
| ------------------------------------------------------------------- | ------------------------ | ----------------------------------------------- |
| 满屏看不见的子弹还在打人                                                        | 只 `visible = false`，碰撞仍在 | 同时 `monitoring = false` + `collision_layer = 0` |
| 池里闲置子弹仍在跑 `_process`                                                | 隐藏不等于停处理                 | `process_mode = PROCESS_MODE_DISABLED`          |
| 发射后立刻原地自爆                                                           | 上一轮的倒计时/穿透次数没清           | 由 `reset_for_pool()` 统一清                        |
| 位置错乱                                                                | 上一轮的世界坐标残留               | 重置为炮口 `Transform2D`                             |
| 修改 `monitoring` 时报 `Can't change this state while flushing queries` | 在物理回调里直接改                | 一律用 `set_deferred()`                            |

> 最后一个坑值得单独说：`monitoring`、`disabled` 这类属性属于物理服务器的状态，**只能在物理步之外修改**，所以必须 `set_deferred()`。直接在 `_on_body_entered` 里赋值会报错。

### 适用条件与代价

- **值得池化**：对象数量大、创建频繁、结构固定（子弹、特效、伤害数字）。
- **不值得**：每秒只创建几个、或对象状态变异极大（每种都不同，重置成本高于新建）。
- 代价是**内存常驻**（预热的对象一直占着），移动端要按峰值用量设定 `initial_size`，不要盲目开大。

# 四、综合场景分析题

## 11. 500 个商贩 NPC 的性能问题

先说我的判断顺序：**这份需求里最可疑的不是"500 个"，而是"每 3 秒"和"头顶 UI"。** 前者是尖峰，后者是 draw call 与字体 shaping。

### 瓶颈一：500 个独立头顶 UI（最可能的主因）

**问题**：每个 NPC 一个 `Label` / `Label3D`，意味着每帧要处理 500 个 CanvasItem 的变换与绘制。若文本各不相同，字体 shaping（字形排布、图集查找）也无法缓存复用，移动端 GPU 上很容易出现几百个 draw call，加上半透明文本的 overdraw，直接压垮填充率。

**方案（按收益排序）**：

1. **可见性剔除**：给每个 NPC 挂 `VisibleOnScreenNotifier2D/3D`，离开视口就 `hide()` 并停止更新文本。实际同屏可能只有 20–50 个。
2. **标签池**：全局只保留 N 个（如 30 个）`Label`，每帧挑选离镜头最近的 N 个 NPC，把文本写进去并定位；其余不创建 UI。**节点数从 500 降到 30**。
3. **只在该变的时候改 `text`**：缓存上一次的价格数字，值没变就不写。赋值会触发重排与图集查询，是最贵的一步。
4. 若文本样式统一，尽量共用同一 `Font` 与主题，避免每个 Label 走不同字体资源。

**验证**：Monitors 里看 `Draw Calls`、`Object Count`、`Process Time`；在 Profiler 里看 `CanvasItem`/`TextServer` 的耗时占比。

### 瓶颈二：500 个计时器同时到期造成的单帧尖峰

**问题**：如果 500 个 NPC 是同一时刻生成的，`Timer` 的 timeout 会高度聚集，每 3 秒来一次 CPU 尖峰。表现就是"平时挺顺，每 3 秒顿一下"——这正是题目描述的 Jank。

**方案**：

1. **错峰（最简单有效）**：初始化时给每个 NPC 一个随机相位

   ```gdscript
   timer.start(3.0)
   timer.wait_time = 3.0
   # 首次触发时间随机打散到 0~3 秒内
   timer.start(randf() * 3.0)
   ```

   500 次摊到 3 秒内 ≈ 每秒 167 次，尖峰消失。
2. **集中调度**：干脆不用 500 个 `Timer`，用一个全局调度器维护索引，每帧只处理固定配额（如 8 个），轮转整份列表。这样单帧开销恒定、可控。

**适用条件**：允许价格延迟几十到几百毫秒生效——对商贩报价来说完全可接受。

**验证**：Profiler 里看帧时间曲线是否还有周期性尖峰；在 `_on_timer_timeout` 里临时插入 `Time.get_ticks_usec()` 打点，统计单帧调用次数。

### 瓶颈三：500 个 Timer 节点本身的开销

**问题**：即使错峰，500 个 `Timer` 也是 500 个节点 + 500 次回调派发。`Node` 的管理（进入树、每帧遍历、信号派发）在移动端并不便宜。

**方案**：**数据与表现分离**。500 个商贩的"报价数据"放在一个数组里（纯数据，不是节点），只有进入玩家附近范围的几十个才实例化可视化场景。远处的商贩根本不存在节点，自然没有 UI、没有 Timer、没有物理。

这是这类"大地图 + 大量 NPC"最根本的架构修正，收益远大于任何微优化。

**验证**：Remote Scene Tree 里看节点总数；`Performance.get_monitor(Performance.OBJECT_NODE_COUNT)` 输出到 HUD 观察进出范围时的数量变化。

### 瓶颈四（补充）：物理与碰撞

**问题**：若每个商贩都带 `CollisionShape2D` 参与碰撞检测，500 个 body 的宽相位遍历与形状更新也是开销；且大多数商贩根本不需要物理交互。

**方案**：

- 非交互 NPC 去掉物理体，交互改用距离判断（`distance_squared` 比较，避免开方）。
- 必须保留物理的，用 `collision_layer/mask` 分层，只让"附近 + 可交互"的进入检测。
- 静态不动的用 `StaticBody2D`，并开启 `PhysicsServer2D` 的静态宽相位优化。

**验证**：Profiler 里看 `Physics 2D` 分类；Monitors 里看 `Physics 2D Active Objects`。

### 我实际会怎么定位

不做猜测，按这个顺序走：

1. **Monitors 先看总量**：FPS、`Process Time`、`Physics Time`、`Object Count`、`Node Count`、`Draw Calls`。先判断是 CPU 还是 GPU 瓶颈。
2. **Profiler 看分布**：帧时间曲线如果呈周期性尖峰 → 计时器聚集；如果平稳偏高 → 每帧固定开销（UI 绘制、节点遍历）。
3. **二分法验证**：临时把 500 个 NPC 关掉一半，看帧时间是否近似线性下降。线性 → 单对象成本；非线性 → 存在批量/批处理失效。
4. **移动端专项**：Android 用 AGI / Snapdragon Profiler 看 GPU 与填充率；iOS 用 Xcode Instruments（Time Profiler + GPU Frame Capture）。
5. **回到代码**：临时在可疑函数里 `Time.get_ticks_usec()` 打点，累计 100 帧取平均，定位到具体语句。

### 一句话总结

> 先错峰消除尖峰，再把「数据」和「节点」拆开，最后才谈批处理与底层渲染。**500 个对象在移动端不是数量问题，是"每帧都为每一个对象付固定成本"的问题。**
