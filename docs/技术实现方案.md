# 技术实现方案

> 配套文档：[策划案](策划案.md)
> 目标：用 Godot 的节点、场景、资源、信号把这道题做成一个"能被读懂的工程"，而不只是能跑的脚本。

---

## 1. 六条实现原则

| # | 原则 | 具体做法 | 反面（要避免的） |
| --- | --- | --- | --- |
| 1 | **场景即组件** | 每个界面/元件都是独立 `.tscn`，能单独 F6 运行调试 | 一个巨大的 `main.tscn` 塞所有控件 |
| 2 | **信号向上，调用向下** | 子节点发信号，父节点调用子节点方法 | 父节点 `_process` 轮询子节点状态 |
| 3 | **数据即资源** | 符文、文案、目标序列用 `.tres` 自定义 `Resource` | 把文案硬编码在各个脚本里 |
| 4 | **纯逻辑不进场景树** | 规则抽成 `RefCounted` 的 `GameState` | 逻辑写成 AutoLoad 或塞进 UI 脚本 |
| 5 | **布局交给容器** | 全用 `VBox/HBox/Center/Margin/PanelContainer` | 手摆锚点与 offset |
| 6 | **一份场景，多份数据** | 番外复用同一个 `rune_puzzle.tscn`，只换 `PuzzleConfig` | 复制一份场景改文案 |

第 6 条是整份方案的核心手法：**第一阶段的谜题和番外的反向谜题，共用同一个场景、同一条判定代码，只是喂进两份不同的 `.tres`。** 这样既保证了隔离（数据层隔离），又避免了复制粘贴（工程层复用）。

## 2. 节点树

### 2.1 主场景 `main.tscn`

```
Main (Node)                                  ← 纯逻辑宿主，无视觉
├─ GameFlow (Node, game_flow.gd)             ← 流程状态机，持有 GameState
├─ Backdrop (CanvasLayer, layer=-100)        ← 背景层，不参与 UI 布局
│  ├─ Sky (ColorRect + sky.gdshader)         ← 夜海渐变
│  ├─ Fog (ColorRect + fog.gdshader)         ← 流动迷雾（可调密度）
│  ├─ Sea (ColorRect)                        ← 海面反光带
│  └─ Lighthouse (Node2D)
│     ├─ Tower (Polygon2D)                   ← 塔身剪影
│     ├─ BeamPivot (Node2D)
│     │  ├─ Beam (Polygon2D)                 ← 光柱
│     │  └─ BeamCore (Polygon2D)             ← 光柱内芯（更亮）
│     └─ BeamGlow (CPUParticles2D)           ← 塔顶微光
├─ Fx (CanvasLayer, layer=0)                 ← 特效层
│  ├─ StarBurst (CPUParticles2D)             ← 成功星屑
│  └─ ShakeRoot (Control)                    ← 震屏载体（改 offset）
├─ ScreenHost (CanvasLayer, layer=10)        ← 界面层
│  └─ Host (Control, full rect)              ← 运行时只挂一个 screen
├─ Overlay (CanvasLayer, layer=50)           ← 转场/遮罩
│  └─ Fade (ColorRect)                       ← 淡入淡出
└─ Audio (Node, audio_manager.gd)            [AutoLoad 亦可]
   ├─ SfxClick / SfxCorrect / SfxWrong
   └─ Ambience
```

**为什么分三个 CanvasLayer**
- `Backdrop` 不随 UI 缩放，且可以被震屏排除；
- `Fx` 在背景之上、UI 之下，粒子不会糊住文字；
- `Overlay` 永远最上，转场淡入淡出不会被任何界面盖住。

`layer` 用负数/正数显式指定，保证渲染顺序不依赖同级节点的排列。

### 2.2 小游戏 `rune_puzzle.tscn`（第一阶段与番外共用）

```
RunePuzzle (Control, rune_puzzle.gd)
└─ MarginContainer
   └─ VBoxContainer
      ├─ Header (HBoxContainer)
      │  ├─ TitleLabel (Label)
      │  └─ Attempts (HBoxContainer)          ← 运行时按 max_attempts 生成灯
      ├─ PromptLabel (Label)
      ├─ HintPanel (PanelContainer)           ← 仅 hint_enabled 时 visible
      │  └─ MarginContainer → HintLabel (RichTextLabel, BBCode)
      ├─ RuneRow (HBoxContainer)              ← 运行时按 PuzzleConfig.runes 生成
      ├─ SlotRow (HBoxContainer)              ← 运行时按目标长度生成
      └─ FeedbackLabel (Label)                ← 判定反馈，淡入淡出
```

**动态生成的两个容器**（`RuneRow` / `Attempts` / `SlotRow`）是这个场景的关键：
- 符文按钮不是手工摆三个，而是 `for rune in config.runes: RuneRow.add_child(RuneButton.new(rune))`
- 目标序列长度变了、符文数量变了，UI 自动跟随
- 番外只要换一份 `PuzzleConfig`，界面结构不用动

### 2.3 元件场景

| 场景 | 根节点 | 职责 | 对外信号 |
| --- | --- | --- | --- |
| `story_view.tscn` | Control | 剧情文本 + 两个选项 | `chosen(hint_enabled: bool)` |
| `rune_puzzle.tscn` | Control | 三符文输入与判定 | `completed(success: bool)` / `input_changed(input, attempts_left)` |
| `ending_view.tscn` | Control | 结局文本 + 重开 + 番外入口 | `restart_requested()` / `extra_requested()` |
| `rune_button.tscn` | Button | 一枚符文：自绘字形 + 悬停 + 点击 | `pressed`（内建） |
| `rune_slot.tscn` | Control | 一个输入槽（空/已填） | — |
| `attempt_lamp.tscn` | Control | 一盏剩余次数灯（亮/灭） | — |
| `dialogue_box.tscn` | Control | 番外对话逐句推进 | `finished()` |

> 每个元件都**可单独 F6 运行**：`rune_button.tscn` 单独跑起来就能看字形和悬停效果。这是"场景即组件"的实际收益，也是调试速度的来源。

## 3. 信号契约

### 3.1 连接图

```
StoryView ──chosen(hint)──────────► GameFlow.begin_puzzle(hint)
RunePuzzle ──completed(success)────► GameFlow.settle(success)
EndingView ──restart_requested()───► GameFlow.restart()
EndingView ──extra_requested()─────► GameFlow.begin_epilogue()
GameFlow ──phase_changed(phase)────► Main.swap_screen(phase)
RuneButton ──pressed────────────────► RunePuzzle._on_rune_pressed(rune)
```

### 3.2 三条纪律

1. **子不认父**：子场景不知道该由谁接它的信号，只用 `signal` 声明并 `emit`。父节点在 `_ready` 里 `connect`。
2. **父不改子状态**：父节点只调用子节点的公开方法（`puzzle.configure(config, hint)`），不去摸子节点内部节点路径。
3. **不用 `_process` 轮询**：整个工程除了 shader 与 Tween，没有一处靠每帧读状态推进流程。

## 4. 数据层：自定义 Resource

### 4.1 `RuneDefinition`

```gdscript
class_name RuneDefinition
extends Resource

enum Glyph { STAR, TIDE, WIND }

@export var id: StringName            ## "star" / "tide" / "wind"
@export var display_name: String      ## "星象" / "海潮" / "季风"
@export var glyph: Glyph
@export var tint: Color
@export var stroke_seed: int = 0      ## 决定程序化笔画的抖动
```

一个符文 = 一个 `.tres`：`resources/runes/star.tres` 等三份。

### 4.2 `PuzzleConfig`

```gdscript
class_name PuzzleConfig
extends Resource

@export var title: String
@export var prompt: String
@export var runes: Array[RuneDefinition]
@export var target_sequence: Array[StringName]   ## ["star","tide","wind"]
@export var max_attempts: int = 2
@export var unlimited_attempts: bool = false     ## 番外用
@export var hint_text: String
@export var feedback_correct: String
@export var feedback_wrong: String
@export var feedback_failed: String
```

两份实例：

| 资源 | target_sequence | max_attempts | unlimited | hint |
| --- | --- | --- | --- | --- |
| `main_puzzle.tres` | `[star, tide, wind]` | 2 | false | 星光开航，潮汐同行，最后听风而行。 |
| `epilogue_puzzle.tres` | `[star, wind, tide]` | 2 | **true** | （空） |

> 这就是"一份场景，多份数据"的落点。判定代码只认 `PuzzleConfig`，不认识"第一阶段"或"番外"。

### 4.3 文案资源

剧情与结局文案放进 `StoryScript` / `EndingScript` 资源，字段为 `String`/`Array[String]`。好处：改文案不用碰代码，且可以把策划案里的定稿直接搬进检查器。

## 5. 逻辑核心：为什么 `GameState` 不是 Node

```gdscript
class_name GameState
extends RefCounted
```

**刻意不做成 Node**，理由四条：

1. 它不该进场景树 —— 树的增删、`pause`、`queue_free` 都不应该影响规则；
2. `RefCounted` 可以在无窗口的 headless 环境里单测（`tests/test_game_state.gd`）；
3. 复用一个新实例就是一次干净复位 —— `state = GameState.new()` 结构性地保证"重启后不残留任何字段"，比手动挨个清空可靠；
4. 它不持有任何节点引用，因此没有悬空指针风险。

API 设计（判定逻辑全部在这里，UI 一行判定都不写）：

```gdscript
func begin(hint_enabled: bool) -> void
func push_rune(rune_id: StringName) -> PushResult
func can_accept_input() -> bool
func reset() -> void
```

`push_rune` 返回一个**结构化结果**而不是直接改 UI：

```gdscript
class PushResult:
    var accepted: bool          ## 是否被接受（结算后一律 false）
    var judged: bool            ## 本次是否触发了判定
    var success: bool
    var attempts_left: int
    var cleared: bool           ## 是否清空了输入
```

UI 只负责把这个结果翻译成表现（亮灯、震屏、切界面）。判定的正确性因此与画面完全解耦。

## 6. 布局：全部交给容器

不在任何 `.tscn` 里手写 `offset_left/top/right/bottom`，只用容器与 `custom_minimum_size`。

```
ScreenRoot (Control, anchors full rect)
└─ CenterContainer
   └─ PanelContainer (custom_minimum_size = 720 x 0)
      └─ MarginContainer (theme_override_constants/margin_* = 40)
         └─ VBoxContainer (theme_override_constants/separation = 24)
            ├─ TitleLabel
            ├─ BodyRichText (RichTextLabel, bbcode_enabled, fit_content)
            ├─ Spacer (Control, custom_minimum_size.y = 8)
            └─ Choices (HBoxContainer, alignment=center, separation=32)
```

`RichTextLabel` 承载剧情正文 —— 一个节点就能做分段、加粗、渐显，不需要拆成一堆 Label。

间距、字号、颜色全部收进一个 `Theme`（`resources/theme/main_theme.tres`），通过 `project.godot` 的 `gui/theme/custom` 全局生效。**控件不逐个设属性**，改风格只改一处。

## 7. 动效分工

三种手段各管一段，不混用：

| 手段 | 负责 | 例子 |
| --- | --- | --- |
| **Shader** | 大面积、连续、每帧变化的场 | 雾的流动与收拢、天空渐变 |
| **AnimationPlayer** | 需要长期循环、可在编辑器里预览的动画 | 光柱摇摆（`rotation` 循环） |
| **Tween（代码创建）** | 一次性的、由事件触发的过渡 | 符文笔画生长、灯灭、震屏、文字淡入 |

### 7.1 符文笔画生长

`RuneButton` 暴露一个 `draw_progress: float`，Tween 它，setter 里 `queue_redraw()`：

```gdscript
var draw_progress := 0.0:
    set(v):
        draw_progress = v
        queue_redraw()

func play_draw() -> void:
    create_tween().tween_property(self, "draw_progress", 1.0, 0.28)
```

`_draw()` 里按 `draw_progress` 只画出部分路径 —— 于是"符文被写出来"这件事不需要任何序列帧素材。

### 7.2 震屏

震 `Fx` 层里的 `ShakeRoot.offset`（一个 Control 的 `position`），而不是震整个 CanvasLayer —— 这样背景层和 UI 层的位移可以分别控制，也避免影响到 `Overlay` 的遮罩。

```gdscript
func shake(intensity := 6.0, duration := 0.25) -> void:
    var t := create_tween()
    for i in 3:
        t.tween_property(shake_root, "position",
            Vector2(randf_range(-i2f(i), 0.0), 0.0), duration / 6.0)
    t.tween_property(shake_root, "position", Vector2.ZERO, duration / 2.0)
```

### 7.3 雾收拢

`fog.gdshader` 暴露 `uniform float density : hint_range(0.0, 1.0)`，每错一次 tween 加一档：

```gdscript
create_tween().tween_property(fog_mat, "shader_parameter/density", target, 0.6)
```

## 8. 音频：一个 AutoLoad

整个工程只有一个 AutoLoad：`AudioManager`。

理由：音效会被剧情、谜题、结局三个场景同时需要；如果每个场景各挂一个 `AudioStreamPlayer`，要么重复，要么找不到人管生命周期。

```gdscript
# audio_manager.gd (AutoLoad)
func play_click() -> void
func play_correct() -> void
func play_wrong() -> void
func set_ambience(on: bool) -> void
```

除了这一个，**不引入任何其他 AutoLoad** —— 全局状态越少越好。

音频素材由 Python 程序化合成 WAV（正弦/噪声包络），无版权问题，也顺带展示了"素材不依赖外部下载"。

## 11. 截图自动验收

**目标：把「看起来对」变成「有截图作为证据」。** 每个关键状态落盘一张图，验收时逐张对照清单，而不是凭记忆点头。

### 11.1 为什么必须加这一环

这道题的失分点绝大多数是**视觉可见的状态错误**：

- B 路径下提示条没真正隐藏（`visible` 设了但父容器仍在布局）
- 第一次错后次数灯没灭、或数字没跟着减
- 中文渲染成方块
- 文字溢出面板、按钮被裁切、元素重叠
- 结算后界面没锁住，玩家还能点

**这些单元测试一个都抓不到** —— 单测保证"规则算对了"，截图保证"算对的结果真的被人看见了"。两者是不同层次，缺一不可。

而且截图落盘之后：验收可复查、返工有据、能直接进流程文档。

### 11.2 驱动链路

MCP 已经具备全部能力，不需要额外插件：

| 能力 | 工具 | 用途 |
| --- | --- | --- |
| 启动游戏 | `project_run(mode="main")` | 拉起运行实例 |
| 状态跳转与读值 | `editor_manage(game_eval)` | 在游戏内执行 GDScript |
| 输入模拟 | `game_manage(input_action / input_mouse)` | 点击、按键 |
| 单帧推进 | `game_manage(next_frame)` | 等动画落定再截 |
| **抓画面** | `editor_screenshot(source="game")` | 运行中游戏的帧缓冲 |

### 11.3 调试桥（仅 debug 构建）

```gdscript
# scripts/debug/debug_bridge.gd
# 仅在 OS.is_debug_build() 为真时挂到 Main 下，导出包内不存在
func goto(preset: StringName) -> void          # 直达指定状态
func snapshot() -> Dictionary                  # 当前状态快照（phase/input/attempts/outcome）
```

可用的 `preset`：

```
story_initial      story_choice_a     story_choice_b
puzzle_empty       puzzle_one         puzzle_two
puzzle_wrong_1     ending_success     ending_failure
ending_restart     epilogue_dialogue  epilogue_puzzle
ending_third
```

**意义：让截图点可确定性复现。** 不靠"一路点过去"，每次验收跑同一批状态，图与图之间可比较。

**安全边界**：`goto` 只在 debug 构建中存在，且不改变 `GameState` 的规则常量 —— 它只是把状态推到某个点，判定逻辑一行不改。

### 11.5 判定标准：每张图固定看四件事

| 维度 | 看什么 | 不合格示例 |
| --- | --- | --- |
| **字形** | 中文完整，无 □ / tofu | 标题变成方块 |
| **布局** | 无溢出、无重叠、无裁切 | 正文顶出面板底边 |
| **状态** | 次数 / 槽位 / 提示可见性 与逻辑一致 | B 路径仍能看到提示条 |
| **层级** | 文字可读、主次分明、对比度足够 | 深色字压在深色底上 |

**每次验收跑同一套标准，不因"赶时间"放宽。** 这是这条流程唯一的价值来源。

```
└─ acceptance.md          ← PASS/FAIL 汇总，失败项附截图与原因
```

`acceptance.md` 的格式：

```
| # | 状态 | 结果 | 备注 |
| S01 | story_initial | PASS | |
| S03 | story_choice_b | FAIL | 提示条仍可见，PanelContainer.visible 未同步 |
| S06 | puzzle_wrong_1 | PASS | 次数灯灭一盏，输入已清空 |
```

### 11.7 与流程文档的联动

**每一张 FAIL 的截图，就是一次真实的「AI 产出被打回」的证据。**

这段流程天然产出面试官最想看的东西：不是我声称"我验收了"，而是"第 3 张图提示条没隐藏，我发现了，这是改后的第 3 张图"。

### 11.8 已知限制（必须写进 README）

| 限制 | 说明 |
| --- | --- |
| **焦点依赖** | 游戏窗口被遮挡/最小化时主循环可能冻结，截图返回陈旧帧（响应里带 `stale_frame`）。验收前必须确保窗口在前台。 |
| **只证明静态** | 截图证明"某一帧长这样"，证明不了"连续操作时序正确"。交互时序靠单测 + 手动走查补。 |
| **首次导入耗时** | 首次抓帧可能拿到空帧，需等 `helper_live` 后再截。 |

## 12. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 中文字体缺失导致方块 | M0 第一件事就验证 `SystemFont` 回退链，不拖到后面 |
| 手写 `.tscn` 锚点/容器出错 | 一律用容器，不写 offset；每个场景写完立即 F6 单跑 |
| 动态生成节点与信号重复连接 | 生成时 `pressed.connect` 前先 `is_connected` 判断，或生成后一次性连 |
| Tween 在界面切换后仍在跑 | 场景切换时 `queue_free()` 会连带失效；Tween 绑定在节点上，节点没了 Tween 自动停 |
| 番外复用同一场景却污染第一阶段 | 判定参数全部来自 `PuzzleConfig`，`GameState` 每次 `new()`，不共享实例 |
| 截图拿到陈旧帧导致误判 PASS | 抓帧前先确认 `game_status` 为 live 且响应里 `stale_frame` 为 false；否则先让窗口到前台再重截 |
| 调试桥泄漏进导出包 | `goto` 与整个 `debug_bridge` 只在 `OS.is_debug_build()` 为真时挂载；导出后回归一次确认不存在 |
